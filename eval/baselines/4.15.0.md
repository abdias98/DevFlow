> **Purpose:** the post-Wave-22 point. Wave 22 added the **framework memory**

> lessons about how DevFlow works, captured from escapes, gate corrections,
> Reviewer false positives, process friction and stack patterns, and loaded by
> every knowledge-base reader through `memory query`. Compare against
> [`4.14.1.md`](./4.14.1.md).
> **Framework commit:** the Wave 22 PR chain (F97–F105), released as 4.15.0.

## 1. Task calibration — recorded 2026-09-26

Re-scored on the release tree with `bats tests/devflow-eval.bats` (all green).
Tasks, fixtures, references and checks are unchanged since 4.14.1, so the
calibration is identical — see [`README.md`](./README.md) §1 for the six-task
table.

## 2. Run scorecards — none

No run was recorded for this version, and re-running the six behavioural tasks
would not measure Wave 22: every one of them is a **single first-shot run in an
empty store**, where `memory query` returns nothing and the framework behaves
exactly like 4.14.1 plus the cost of one extra command. The 4.14.0 scorecards
(all twelve at 100% outcome) still describe what those tasks can show.

## 3. How Wave 22 can be measured

The memory only acts on the **second** encounter with a lesson, so the unit of
measurement is a pair of runs sharing a store — the protocol in
[`eval/README.md`](../README.md) → *Measuring the framework memory*:

1. **Run A** — a task whose trap the model *does* fall into (none of 003–008
   qualifies for Claude Sonnet 5: every bare run passed), with
   `DEVFLOW_HOME=<store>`; the trap is surfaced as a correction or an escape and
   recorded in the abstract.
2. **Run B** — a *different* task with the same trap in another workspace (so the
   project id differs), same store, compared against a control run B′ with an
   empty `DEVFLOW_HOME`.
3. Score B and B′ with `devflow-eval`; the memory's effect is B − B′ on the
   check that probes the trap, and `memory query`'s output in B's transcript
   shows whether the lesson reached the agent at all.

## 4. What is still unknown

- Everything §2 of `4.14.1.md` lists — no task with headroom, one model, one run
  per cell.
- **Whether the memory changes an outcome.** It cannot be measured until a task
  pair with headroom exists.
- **Whether agents capture what the procedure asks.** Friction and escape counts
  are recorded by `devflow-ctl` itself; corrections, false positives and stack
  patterns depend on the agent following `framework-memory.md` → Capture. Real
  cycles, compared with `memory friction report`, are the first evidence.
