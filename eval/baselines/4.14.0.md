### What this shows

**On tasks 005–008, DevFlow did not change the outcome for this model.** Every
bare run avoided the trap its task was built around, unprompted: it sorted
numerically (005), parsed `DEBUG` as a real boolean (006), validated the whole
import file before writing (007), and cached the record rather than the caller's
view of it (008). These tasks have no headroom for a model this capable — they
cannot show a benefit, and 100% on both sides is a ceiling, not a tie that
means the framework does nothing. The traps are classic ones the model already
knows; the calibration (naive references at 76–81%) proves the checks *can*
tell implementations apart, not that a bare run of this model produces one.

This is a different result from 003 and 004, where the bare runs recorded in
[`4.12.0.md`](./4.12.0.md) missed exactly the class each was built for. Those
bare runs were self-run, so before drawing a contrast, note the two are not
comparable: **003 and 004 have not been re-run blind.** They may discriminate
less than 4.12.0 suggested.

### What the outcome score does not capture

The `/devflow-feature` runs did more than the checks measure:

- 005 found and fixed an overflow the plan did not cover (two huge middle values
  summing to `Infinity`), recorded as `(discovered)`, and backlogged that `sum`
  and `mean` share it.
- 006 flagged that `DEBUG=app:*` (the `debug` npm package's convention) would
  make `loadConfig()` throw at startup, and recorded it as an accepted risk.
- 007 backlogged a race between concurrent `add`/`import` processes and a
  non-atomic store write.
- 008 mutation-tested its own suite by breaking the code seven ways; two
  mutations initially passed unnoticed, and the two tests added to close them are
  why the suite now catches them.

Whether any of that is worth its cost depends on what a team values; none of it
moves `Outcome`, which is by design (`Process` never gates pass/fail).

### Cost

Measured from each subagent's own usage report (tokens are that subagent's only):

| Run | Tokens | Wall time |
|-----|-------:|----------:|
| bare 005 / 006 / 007 / 008 | 39,885 / 43,346 / 41,336 / 42,816 | ≈ 20 / 49 / 29 / 43 s |
| `/devflow-feature` 005 / 006 / 007 / 008 | 178,421 / 209,737 / 156,810 / 192,406 | ≈ 588 / 733 / 568 / 891 s |

About **4.4× the tokens and ~20× the wall time**, for the same outcome on these
four tasks.

### Process score — a harness bug, not a framework gap

All four `/devflow-feature` runs score `Process 1/2`. The missing check is
*"Spec or feature plan produced"*: every run did write a plan, at
`docs/devflow/features/*-feature-plan.md`, but `devflow_artifact_any spec plan`
only looks in `docs/devflow/specs/` and `docs/devflow/plans/`. The same gap
affects tasks 001–004 (it is why 4.12.0's runs also scored 1/2). It does not
affect `Outcome`, and is worth fixing separately in `eval/bin/devflow-eval`.

### Wave 21's own mechanisms

Escape analysis and runtime verification are still unexercised: none of the
runs had a post-approval defect to record, and no task declares an externally
observable scenario at `deep`/`maximum` rigor. Nothing here is evidence for or
against them.

## 3. Comparison across 4.10.0 → 4.14.0 — still not possible

4.10.0 and 4.11.0 have no run scorecards, and 4.12.0's (tasks 003/004) were
self-run rather than blind, so there is still no before/after comparison of the
framework against itself. What exists now is one blind cross-section of 4.14.0
against a bare prompt, on tasks 005–008: identical outcomes, at several times the
cost (§2).

What would make a comparison meaningful, in order:

1. **Tasks with headroom.** A task a bare run of the same model already passes
   cannot show a benefit. 005–008 are that; the next tasks need a defect a capable
   model does *not* avoid unprompted — subtler, or requiring project-specific
   knowledge that only a spec/plan/review chain would surface.
2. **Re-run 003 and 004 blind**, to learn whether they discriminate at all
   without the self-run's contamination.
3. **A weaker model.** The suite may separate runs there; this run only measured
   one model.
4. **Escape rate** needs real post-release cycles; no snapshot can simulate it.
