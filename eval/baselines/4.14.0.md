### What this shows

**On every behavioural task, DevFlow did not change the outcome for this model.**
Every bare run avoided the trap its task was built around, unprompted: it sorted
numerically (005), parsed `DEBUG` as a real boolean (006), validated the whole
import file before writing (007), cached the record rather than the caller's view
of it (008), guarded a payment against concurrent double-charging (003) and
dropped a late response for an old selection (004). These tasks have no headroom
for a model this capable — 100% on both sides is a ceiling, not a tie that means
the framework does nothing. The calibration (naive references at 76–83%) proves
the checks *can* tell implementations apart, not that a bare run of this model
produces one.

**This contradicts the 4.12.0 contrast.** [`4.12.0.md`](./4.12.0.md) §2 recorded
bare runs at 83% (003, missing `[concurrency]`) and 82% (004, missing
`[ordering]`), and read them as the effect of Wave 19's scenario derivation.
Re-run blind, the bare runs pass both. The 4.12.0 bare runs were self-run by the
session that had written the tasks, and are not reproducible: whatever they
measured, it was not that a bare run of this model misses those two classes.
Nothing in this file should be read as a reason to believe Waves 18–19 changed an
outcome.

### What the outcome score does not capture

The `/devflow-feature` runs did more than the checks measure:

- 003 wrote real concurrent HTTP tests with a stub charge held in flight, and its
  review raised missing authentication on the new charge endpoints as a BLOCK
  before the Reviewer downgraded it to WARN (the service has no identity model),
  plus the absence of an idempotency key for a lost-response retry.
- 004 backlogged that the Overview loader has the same stale-response flaw and
  left it alone as out of scope — where the bare run silently changed both.
- 005 found and fixed an overflow the plan did not cover (two huge middle values
  summing to `Infinity`), recorded as `(discovered)`, and backlogged that `sum`
  and `mean` share it.
- 006 flagged that `DEBUG=app:*` (the `debug` npm package's convention) would
  make `loadConfig()` throw at startup, and recorded it as an accepted risk.
- 007 backlogged a race between concurrent `add`/`import` processes and a
  non-atomic store write.
- 008 mutation-tested its own suite by breaking the code seven ways; two
  mutations initially passed unnoticed, and the two tests added to close them are
  why the suite now catches them.

Whether any of that is worth its cost depends on what a team values; none of it
moves `Outcome`, which is by design (`Process` never gates pass/fail).

### Process score — a harness bug, fixed

The first eight `/devflow-feature` runs scored `Process 1/2`: *"Spec or feature
plan produced"* looked only in `docs/devflow/specs/` and `plans/`, while the
feature agent writes `docs/devflow/features/*-feature-plan.md`. Fixed by adding a
`feature` artifact type to `devflow-eval` (#170); the rows above are re-scored.
It never affected `Outcome`.

### Wave 21's own mechanisms

Escape analysis and runtime verification are still unexercised: none of the
runs had a post-approval defect to record, and no task declares an externally
observable scenario at `deep`/`maximum` rigor. Nothing here is evidence for or
against them.

## 3. Comparison across 4.10.0 → 4.14.0 — still not possible

4.10.0, 4.11.0 and 4.12.0 have no blind run scorecards (4.12.0's were self-run,
and did not reproduce — §2), so there is no before/after comparison of the
framework against itself. What exists is one blind cross-section of 4.14.0
against a bare prompt across all six behavioural tasks: identical outcomes, at
several times the cost.

What would make a comparison meaningful, in order:

1. **Tasks with headroom.** A task a bare run of the same model already passes
   cannot show a benefit. All six are that. The next tasks need a defect a capable
   model does *not* avoid unprompted — subtler, or requiring project-specific
   knowledge that only a spec/plan/review chain would surface.
2. **A weaker model.** The suite may separate runs there; this run measured one
   model, and only once per cell.
3. **Repeats.** One run per cell cannot distinguish a real 100% from a lucky one.
4. **Escape rate** needs real post-release cycles; no snapshot can simulate it.
