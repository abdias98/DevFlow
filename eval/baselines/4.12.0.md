## 2. Run scorecards — recorded 2026-09-17

> **Update 2026-09-20 — the bare results below did not reproduce.** Re-run blind
> (fresh subagents given only the task's prompt), both bare runs scored 100%:
> 003 passed `[concurrency]` and 004 passed `[ordering]`. See
> [`4.14.0.md`](./4.14.0.md) §2. The numbers below are kept as recorded, but
> should not be read as evidence that a bare run of this model misses those classes.

**Model / editor:** Claude (Sonnet 5), driven directly through the installed
`devflow-feature` skill (`~/.claude/commands/`) and `devflow-ctl` at 4.12.0,
in a fresh git-initialized copy of each task's `fixture/`. **Limitation:**
this is a self-run, not an independent blind evaluation — the same session
that designed the tasks also executed and scored them. It was not told the
scenario classes it would be scored on; the prompt given to both the
`/devflow-feature` and bare runs was the exact, unmodified prompt from each
task's `task.md`. No comparable runs exist yet for 4.10.0/4.11.0 (those
baseline files still hold the calibration only) — re-running this protocol
against a checkout of those earlier commits, with the same prompts, is the
natural next step for a real before/after comparison.

| Task | Run | Outcome | Process | Failed outcome checks | Planned scenarios covering probed classes | Discovered / review findings |
|------|-----|:-------:|:-------:|-----------------------|--------------------------------------------|-----------------------------|
| `003-order-payment-lifecycle` | `/devflow-feature` | **18/18 = 100% ✅** | 1/2 (review artifact only — `feature-plan.md` isn't a recognized "spec\|plan" path for the process check) | none | Yes — `context.md` → Behavior Scenarios named the concurrent-double-pay case (S1) and the declined-charge-then-cancel case (S2) *before* the plan or code existed; the plan's Task 1 designed a synchronous pending→paying claim specifically to satisfy S1 | None discovered mid-implementation (plan already covered every probed class); Reviewer: 0 BLOCK, 1 WARN (a documentation comment), 1 INFO |
| `003-order-payment-lifecycle` | bare | **15/18 = 83% ❌** | n/a | `[concurrency] Two simultaneous payments charge exactly once` | n/a — no framework artifacts | n/a |
| `004-project-panel-tab` | `/devflow-feature` | **17/17 = 100% ✅** | 1/2 (same reason) | none | Yes — `context.md` → Behavior Scenarios explicitly named the Overview tab's *existing* load pattern as lacking a stale-response guard (derived from the Order and Change-while-in-flight Transition Prompts applied to the stated reference implementation, not just to the new tab), before any code was touched | None discovered mid-implementation; Reviewer: 0 BLOCK, 1 WARN (an unconsumed in-flight request note), 1 INFO |
| `004-project-panel-tab` | bare | **14/17 = 82% ❌** | n/a | `[ordering] A late response for an old selection is ignored` | n/a — no framework artifacts | n/a |

Both `/devflow-feature` runs matched `reference/correct/` exactly (100%); both
bare runs matched `reference/naive/` exactly, failing on precisely the one
behavioural check class each task was built to probe. In both cases the
gap-causing behavior was named as a **Behavior Scenario in `context.md` before
any code was written** (Wave 19's intended effect), not discovered later during
implementation or caught only by the Reviewer — for task 004 specifically, the
scenario derivation caught a defect in the *stated reference pattern itself*
(the Overview tab), which the bare run copied faithfully into the Tasks tab
exactly as the task's design predicted a bare run would.

Both `/devflow-feature` runs cost noticeably more than the bare runs: a
session (self-approved in "Standard" mode, no real user pause) including a
plan document, 2 TDD tasks each, a standalone review pass, metrics, and a
knowledge-base write-back, versus a single-pass bare implementation. The eval
harness's outcome/process split makes this visible deliberately: `Process`
never gates pass/fail, so the extra ceremony is credited only through the
`Outcome` it actually bought — which here is the full gap between 82–83% and
100%.

## 3. Comparison across 4.10.0 → 4.11.0 → 4.12.0 — partially pending

4.12.0 now has real run scorecards (above); 4.10.0 and 4.11.0 still only have
calibration. Since the fixtures, references and checks are unchanged across
all three versions, the outcome-vs-version comparison that would show
*whether Waves 18–19 changed anything relative to a pre-Wave framework* still
requires running this same protocol against a checkout of `4.10.0` and
`4.11.0` (with `devflow-feature`/`devflow-ctl` reinstalled from each
commit) with the same two prompts. What 4.12.0's numbers alone show: the
**current** framework, run faithfully, reliably surfaces and fixes both
probed defect classes before code exists — which is what Waves 18–19 were
built to cause. They do not by themselves prove this is an *improvement*
over 4.10.0, only that the current mechanism works when exercised.
